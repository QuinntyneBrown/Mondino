# 0004: The database engine

**Status:** Accepted (journey 2, Open an invite link). Supersedes the part of [0003](0003-backend-baseline.md) that left the engine open.

## Context

ADR 0003 left the database engine open: `Database:Provider` accepted only `InMemory`, which keeps
nothing between runs. Journey 2 is the first that holds a team, so it chooses the engine.
Mondino holds a few small tables (teams, teammates, cities, later sign-in links and moments) that
are read far more than they are written. `AGENTS.md` asks for EF Core, migrations applied by a CLI
command and never on startup, idempotent seed data, and tests on EF Core InMemory only.

## Decision

- **PostgreSQL**, through EF Core and `Npgsql.EntityFrameworkCore.PostgreSQL` 10. It is open
  source, offered as a managed service by every major host, and has the most used EF Core
  provider after SQL Server's. The hosting platform is still open; any that offers PostgreSQL
  fits.
- `Database:Provider` is `PostgreSQL` or `InMemory`. With `PostgreSQL` the connection string is
  `ConnectionStrings:Mondino`, and it is required. `InMemory` stays the default for running the
  API on a laptop with no database, and is what the tests use.
- **Migrations** live in `Mondino.Infrastructure/Persistence/Migrations`, made with
  `dotnet ef migrations add <Name> --project src/Mondino.Infrastructure` from `backend/`. A
  design-time factory (`DesignTimeAppDbContextFactory`) gives the tool a PostgreSQL context
  without a running database. `Mondino.Cli migrate` applies them; the API never does.
- **Seed.** `Mondino.Cli seed` adds the sample team, Northwind, and its twelve teammates when
  they are missing (`NorthwindSeed`). How a team is made by a person is `make-team`'s (journey 5);
  until then the seed is the only way a team and its invite link come to exist.
- **Tests** stay on EF Core InMemory, one store per fixture. No test reaches PostgreSQL.

## Consequences

- A deployed system needs a PostgreSQL database and runs `migrate`, then `seed` if it wants the
  sample team, before it starts the API.
- Nothing in a test proves the migration against a real PostgreSQL. A migration is generated by
  the tool, never written by hand, and is read in review.
- Columns are mapped with EF Core's conventions; anything PostgreSQL-specific is avoided, so a
  later move to another relational engine changes the provider and the migrations, not the model.

## Settings a deployed system needs

| Setting | Value | Why |
|---|---|---|
| `Database:Provider` | `PostgreSQL` | The engine. `InMemory` keeps nothing between runs. |
| `ConnectionStrings:Mondino` | for example `Host=db;Database=mondino;Username=mondino;Password=…` | Where the database is. Kept in the host's secret store, never in a file. |
